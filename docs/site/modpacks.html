    Modpacks: porting any pack to Rusty Minecraft

    Goal (Ludovic, 2026-10-16): support modpacks like All the Mods 10 far better than Minecraft does, and be able to port any of them. "Better" is measured: pack load time, RAM, FPS, TPS and world-generation speed against the same pack on NeoForge or Fabric. "Any of them" means a pipeline, not a list of hand ports. It takes a pack as players download it and produces native Rusty Minecraft mods. The pipeline is AI agents in dependency order, each port checked against the original mod running in a dev-only Java instance.

    This page is the design. It builds on mods.md (content mods, native mods, and why Java jars cannot run in Rusty Minecraft, so we port instead). The ATM10 inventory behind the numbers below is modpacks/atm10-mods.csv.

    In one picture

     pack (.mrpack / CurseForge zip or instance / Prism instance)
   │  import: normalise to pack.json (MC version, loader, files, hashes, overrides)
   ▼
 inventory: every jar's metadata (mods.toml / fabric.mod.json, licence, deps, file census)
   │  classify: content · client-ui · library · performance · server-only · integration · other
   │  tier:     data · logic · machines · deep · client · none
   ▼
 dependency order (libraries first, then the mods that need them)
   │
   ├─ carry-over (mechanical, no agent): assets/ + data/ upgraded to 26.3 formats,
   │    block and item registrations from the oracle's facts export  →  <mod>.hmod
   ├─ port (one agent per mod, tiers logic and up): a Rust native mod (a horizon-mixins
   │    bundle), iterating until its harness passes                  →  <mod>.hnmod
   ├─ harness per mod: the Java mod in a dev-only NeoForge/Fabric oracle vs the port
   ▼
 coverage report: ported · partial · not yet · not needed, per mod and per class

    Everything runs on the player's (or server owner's) machine, on jars they downloaded. The results stay there. See Licences.

    Licences

    Mods have their own licences: many are All Rights Reserved, others MIT, LGPL or MPL. A port is a derivative work. These rules are part of the pipeline, not advice to users:

    1. Local by default. The pipeline runs on the player's or server owner's machine, on jars they downloaded themselves. The ports it makes stay there. This works like prepare with Minecraft's own files: nothing is redistributed.
    2. The licence is recorded per mod in the inventory (license from mods.toml or fabric.mod.json, plus Modrinth's SPDX id where one exists) and travels with the port into its horizon-mod.toml (ported-from = { id, version, license, url }).
    3. Publishing needs permission. A port can go into a mod index, the launcher browser or a server's download list only if its licence allows redistributing derivatives (permissive, or copyleft with the port under the same licence and its source published) or the author has given written permission, recorded in the index entry. The tooling refuses to package anything else. No-derivatives and non-commercial licences (14 in ATM10) are never published. For them, even a local port gets a warning that the licence may not allow it.
    4. Mod code never enters this repository, and nobody reads it. Mod jars, Java oracle builds with mod code, and ports of mods we have no permission to publish all live outside the repo: in the user's pipeline work directory, or for our own development in ~/code/horizon-parity/modports/ (dev-only, never pushed). A mod's code is never decompiled, read, quoted or paraphrased, by people or agents. Ports are written only from the mod's observed behaviour (the oracle and the harness), its own data files and its public documentation. The repository holds the pipeline, the API, metadata (ids, names, versions, licences, counts) and test fixtures we write ourselves.
    5. Contacting authors or publishing any port is Ludovic's call. Agents ask first.

    This is engineering policy, not legal advice. Before anything is published, Ludovic decides, with advice if needed.

    Registries 0.2: data-driven blocks, items and mob effects

    A content mod (.hmod) carries assets/ and data/ and no code:

    ruby.hmod
├── horizon-mod.toml          id = "ruby", api = "0.2", side = "both", capabilities = ["registries"]
├── data/ruby/horizon/block/ruby_block.json
├── data/ruby/horizon/item/ruby.json
├── data/ruby/recipe/ruby_block.json            (26.3 data-pack formats)
├── data/ruby/loot_table/blocks/ruby_block.json
├── data/minecraft/tags/block/mineable/pickaxe.json   (adds to a vanilla tag)
├── assets/ruby/blockstates/ruby_block.json     (26.3 resource-pack formats)
├── assets/ruby/models/block/ruby_block.json
├── assets/ruby/items/ruby.json
├── assets/ruby/textures/block/ruby_block.png
└── assets/ruby/lang/en_us.json

    A block declaration names a template, a vanilla block whose behaviour class, state properties and shapes the new block takes, and overrides what differs:

    {
  "template": "minecraft:iron_block",
  "properties": { "hardness": 5.0, "explosion_resistance": 6.0, "sound": "minecraft:metal",
                  "map_color": 33, "light": 0, "requires_tool": true },
  "item": true
}

    A block may define shapes to replace both its selection outline and collision shape. It selects a list of boxes by one template state property:

    "shapes": { "property": "axis", "values": {
  "x": [[0, 0.25, 0.25, 1, 0.75, 0.75]],
  "y": [[0.25, 0, 0.25, 0.75, 1, 0.75]],
  "z": [[0.25, 0.25, 0, 0.75, 0.75, 1]]
} }

    Each box is [min_x, min_y, min_z, max_x, max_y, max_z] in block units. Each value of the template property needs an entry. Up to 16 boxes form a union; an empty list is an empty shape. Invalid bounds or values reject the content root. Without shapes, both shapes remain the template's. Other properties such as occlusion, light, and support still come from the template.

    A declaration may also set "default_state": {"facing": "north"}. The map changes only those state properties on the template's default; omitted properties keep their template values. Names and values must identify exactly one template state, or the content root is rejected. Leave the map out to keep the template default.

    Most decoration and resource blocks are vanilla classes with other numbers: Macaw's doors are DoorBlocks, XTones are full cubes, ore sets are DropExperienceBlocks. So templates cover the data tier without code. Templates also give mod blocks every behaviour Rusty Minecraft already implements and the harnesses already check. Items work the same way ("template": "minecraft:diamond", overriding max_stack_size, rarity, crafting_remainder and any data component in components; a block's item takes components too).

    How the game loads them, without touching vanilla's path:

    • Rusty Minecraft reads everything from one resource root. Resource packs already work as an overlay root (packs::startup_root) with vanilla's files linked and the overridden ones rewritten. Content mods add one more layer: the enabled mods' assets/ and data/, and the prepared per-state tables (facts.json, gameplay-facts.json, block-behaviours.json, the collision, occlusion and movement tables, model-states.json, render-definitions.json, items.json, ...). Each table gets the mod blocks' rows appended, copied from the template's rows with the declared overrides. The loaders then read one tree and need no mod-specific code.
    • Vanilla state ids do not move. Mod states are appended after vanilla's, mods in id order, so the same mod set gives the same ids. Saves store block names, so ids never reach the disk.
    • Loaders that read only data/minecraft/ (recipes, loot, tags) read every namespace, as vanilla does. With no mods there is only minecraft, so nothing changes.
    • Namespaces. A mod's files go under its id, and under the namespaces its manifest lists when its Java original ships them so (namespaces = ["kaisyn", "towns_and_towers"] for Towns and Towers, mod id t_and_t; docs/mods.md). No namespace has two owners: a mod whose id or listed namespace another mod that is on already owns is left out, with both named in the log. horizon-port-pack avoids that inside a pack: a namespace two carried mods both claim (YUNG's structure mods all ship files under yungsapi, the namespace of YUNG's API, whose own jar isn't carried) is left to none of them, and its files stay outside. The launcher applies the game's rule before it starts a pack (pipeline::loadable) and lists what it left off.
    • The overlay is built on the first start with a set of mods and kept for later starts. A stamp (horizon-mod-content.stamp) hashes the game executable, the base tables and every mod file's size and mtime. Adding, removing or editing a mod, or a new build of Rusty Minecraft, rebuilds it. For ATM10's 40 data-tier mods the build takes about a minute of the first start on a busy machine.
    • Worldgen. Mods' structures, structure sets, template pools, processor lists, configured and placed features join the worldgen/*.json bundles. Their structure templates go under worldgen/structure/<ns>/. Their biome tags are merged into worldgen/biome_tags.json, minus the biomes and tags Rusty Minecraft does not have. Mod biomes, noise and density functions are not carried yet.
    • Limits. Chunk sections size their global palette to the registry: 16 bits for vanilla's 35,723 states (the same chunks, saves and packets as before), one more bit each time content mods double it, up to 2^20 states (1,048,576). Past that the content root is refused with the states per mod. ATM10's 42 carried mods take the registry to 193,762 states (18 bits). On the network the width is the registry's: unchanged for vanilla clients as long as no content mod is on, wider only between Rusty Minecrafts that share the same mods; a Rusty Minecraft with content mods still reads a vanilla server's 16-bit chunks. Block sprites fill texture arrays of 2048 layers, eight at most (16,384; vanilla takes 1,250, identical textures share a layer; ATM10's 42 take 9,790).
    • Broken mod files load as vanilla loads them. A blockstate definition that does not bind (a multipart value the block does not have), a block model that is missing or does not parse, and a recipe that does not parse are logged and skipped: the block gets no model or the missing model, the recipe is absent, everything else loads. Vanilla's own files never hit these paths.
    • Not in 0.2: multiplayer registry sync (single player and the integrated server first), worlds opened without a mod they used (vanilla turns unknown blocks into air; we will ask first), vanilla ids redefined by a mod (refused).

    The pipeline: horizon-port-pack

    A Rust tool in this repo (crates/horizon-port-pack, a CLI the launcher also calls), modelled on the version-port pipeline (tools/version_port.py: detect, diff, regen, harnesses, report, publish). Each step reads and writes files in a work directory, so it can be rerun, resumed and inspected:

    <work>/                       ~/.horizon/ports/<pack-slug>/ for players; ~/code/horizon-parity/modports/ for us
├── pack.json                 normalised import
├── inventory.json            per mod: metadata, licence, census, class, tier, deps, layer
├── jars/                     the user's own jars (copied or linked from their instance), never uploaded
├── mods/<id>/
│   ├── carry/                assets/ + data/ upgraded to 26.3
│   ├── oracle/               facts, registries and traces exported from the Java oracle
│   ├── port/                 the agent's Rust crate (tiers logic and up)
│   ├── harness/              per-mod harness results and logs
│   └── <id>.hmod
└── coverage.json, coverage.md

    Status. import, inventory, fetch, carry and report run today, and port runs them all for what a player's machine can port (content mods of the data tier), as the launcher's "Import modpack" does:

    cargo run -p horizon-port-pack -- import ~/Downloads/pack.mrpack ~/.horizon/ports/pack
cargo run -p horizon-port-pack -- inventory ~/.horizon/ports/pack     # --offline reuses modrinth.json
cargo run -p horizon-port-pack -- fetch ~/.horizon/ports/pack         # the portable mods' jars, or name them
#   --from <folder>: copy the player's own jars (an installed instance, a downloads folder)
cargo run -p horizon-port-pack -- carry ~/.horizon/ports/pack         # content mods with a jar, or name them
#   --resources <prepared root>: only templates Rusty Minecraft's tables have
cargo run -p horizon-port-pack -- report ~/.horizon/ports/pack        # coverage.json and coverage.md
cargo run -p horizon-port-pack -- port ~/Downloads/pack.zip ~/.horizon/ports/pack [--from <folder>] [--resources <root>]

    Resource packs from an imported modpack

    Import stages embedded resource packs in <work>/resourcepacks/: .mrpack common overrides and client overrides (the client copy wins), a CurseForge ZIP's declared override folder, or an installed instance's resourcepacks/ directory. ZIP packs stay intact; directory packs must contain pack.mcmeta. Server-only overrides and unrelated files such as scripts and options.txt are not copied.

    port also obtains client-supported .mrpack resource-pack ZIPs from the existing permitted download hosts, checking the index's SHA-1 before keeping them. <work>/resourcepacks.json records available, missing, failed, conflicting and unsupported entries; they also appear in coverage.json and coverage.md. A copied pack is reported as partial, not as a rendering-verified port. Shader packs are reported as pending conversion. Old import folders without this report still open.

    The launcher copies staged packs into <work>/home/resourcepacks/ on import, port and launch. It preserves any existing profile pack as a whole, including edits inside a directory pack, and lists name/content conflicts. <work>/profile-resourcepacks.json records those results. A profile with resource packs and no carried mods can play. Enable packs in the game's Resource Packs screen; importing never changes the enabled-pack list.

    Paths must stay within staging, links are refused, and one import is limited to 65,536 resource files and 512 MiB of resource bytes (including both override layers). Indexed downloads are limited to 512 MiB each. These checks use synthetic packs and temporary profiles; in-game rendering still needs Minecraft 26.3 prepared resources and has not been verified for this local batch.

    check <jar> <out> takes one mod jar on its own, as the launcher's mod browser installs it (mod-browser.md): it carries the jar into <out>/carry/ and reads its class files (constant pool, superclass, declared methods; no decompiling) for what the carry can't take, then writes the verdict to <out>/check.json. Works: content only, and the code just registers it. Partly: the content ports, and the code features listed don't (block entities, menus, entities, blocks and items with behaviour of their own, recipe types, Mixins, game events). Doesn't run: nothing to port, or a jar made for 1.20 or older. Each mod class is followed up to the first game class it extends; a block subclass that only overrides how it looks or is placed (getStateForPlacement, rotate...) is registration. Game classes are read by Mojang's names (26.1 and later, and NeoForge since 1.20.5); older Fabric jars name them in intermediary, so a class extending one counts as code that can't be read. On ten 26.3 jars (2026-10-22): Macaw's Fences, Windows and Furniture, Ecologics, Compressed Blocks, More Decorative Blocks and Moog's Nether Structures are Partly; Sodium and GeckoLib don't run (Mixins, renderers, nothing to port); Fabric API doesn't run (its id has a dash, which content mods can't use). A check takes 0.2 s to 3 s, and 24 s for Compressed Blocks (18 MB, 9,360 recipes, writing the carry dominates).

    fetch gets each jar the player's way, never from us: copied from a folder they have (matched by SHA-1, or through a CurseForge app instance's minecraftinstance.json), else downloaded from the link the pack itself gives (a .mrpack's, on the format's hosts only) or, for a CurseForge pack, the same file on Modrinth's public CDN, found by its SHA-1. Without jars, classes come from the reviewed table, Modrinth categories and sides; with jars, from their mods.toml / fabric.mod.json and file census too. On Create+ 6.0.0 alpha f (155 files, metadata only): content 54, library 33, client-ui 26, performance 25, other 14, unknown 2, server-only 1; 40 rows matched the reviewed ATM10 table; three dependency layers (93 / 57 / 5).

    carry copies a jar's assets/<id>/, data/<id>/, data/minecraft/tags/ and data/c/tags/ into mods/<id>/carry/, a folder content mod (API 0.2) the game loads with --dev-mod, and keeps what a content mod may not hold (other namespaces, vanilla data) in outside/. Vanilla skips them one by one. A byte-order mark is dropped. For ATM10's 42 mods that is 6 files in 4 mods, and the 42 load as carried. No class file is copied. It upgrades from 1.21.1 to 26.3: vanilla-type recipes (ingredients), loot tables (conditions lists become one condition, functions become modifier, kinds move to type, tool matches on silk touch or shears become minecraft:tool/can_silk_touch and minecraft:tool/can_shear, and number providers written as a bare {"min", "max"} get "type": "minecraft:uniform"), and the items/ definitions 1.21.4 introduced. 1.21.1 read such a bare range as uniform and 26.3 refuses it: 304 of ATM10's carried tables have them (rolls, counts, enchantment levels), and before the carry typed them their chests came out empty or short.

    Blocks and items come from the NeoForge oracle when <work>/oracle/facts.json exists (step 6): every block the mod registers gets the vanilla template of the same vanilla class and states whose shapes, sounds, set type and wood type match best, with the mod's own hardness, blast resistance, light, tool need, friction, map colour and sounds as overrides. --resources <prepared> limits templates to blocks Rusty Minecraft's tables have. carry-report.json lists, per block, what the template does not reproduce (other shapes, sounds no vanilla block has, a class of its own), and the blocks left out: those whose vanilla class has no vanilla block with the same states (Macaw's garage doors, multi-part gates). An item of a vanilla tool or armour class (SwordItem, PickaxeItem, ArmorItem, ...) gets the iron item of that class and slot as its template, and the oracle's durability, attribute modifiers, tool rules, enchantability and repair items as a component patch over it, minus what the template already has (--resources gives the template's components); other items keep minecraft:stick. Armour of the mod's own material gets a 26.3 equipment asset (assets/<ns>/equipment/<material>.json) made from its 1.21.1 layers, their textures/models/armor/<name>_layer_1.png and _layer_2.png copied to textures/entity/equipment/humanoid/ and humanoid_leggings/, and its equippable names that asset and the material's equip sound. A material with no asset to name (layers elsewhere, another mod's) draws the template's armour, reported as a difference. Recipes get the convention tags they use (c:dyes/red), filled from the oracle with vanilla's and the mod's own members. Without the oracle, templates are guessed from the blockstate's properties: the template whose properties include them with the fewest left over (models often ignore powered or waterlogged), the block's name breaking ties (_pane, _gate, _trapdoor). Walls and vines have the same property names; sides tested as true / false make a vine (Chipped's 11 vines, which the game refused as walls: their blockstates did not load).

    2. Inventory and classification

    Per jar, without decompiling:

    • Metadata: META-INF/neoforge.mods.toml / META-INF/mods.toml / fabric.mod.json: id, version, license, authors, URLs, dependencies with ordering and side, mixin configs, access transformers.
    • Census of files: blockstates (≈ blocks), item models (≈ items), recipes, loot tables, tags, worldgen files, structure NBTs, languages, sounds, textures; the number of mixins and the vanilla classes they target; whether the jar has code beyond its data.
    • Census of classes: the superclass names in the class files (constant pool only): how many block entities, menus, screens, entities, renderers, recipe serializers, payload types.
    • Known mods: a reviewed table in the repo (id → class, tier, Rusty Minecraft equivalent: "sodium: performance, built in", "jei: client-ui, recipe viewer built in") wins over heuristics. It starts with ATM10's 495 rows.

    Class rules, in order: the known-mods table; client-only side → client-ui; server-only side → server-only; mixins only, into rendering or ticking, no content → performance; no content and depended on by others → library; depends on two or more content mods and adds little → integration; otherwise content. Tier rules: content with no code beyond registration → data; behaviour callbacks only → logic; block entities or menus → machines; entities, renderers, dimensions or mixins into gameplay → deep.

    3. Dependency order

    A topological order over required dependencies, libraries first. Each mod gets a layer (0: needs nothing in the pack). A mod is ported only after its dependencies are ported or mapped to the API. A library mapped to the API ("Curios → accessory slots") counts as done when that API feature exists. Cycles (rare: optional mutual integrations) are broken at optional edges.

    4. Carry-over: data and assets

    Mechanical, the same for every mod, and no agent:

    1. Extract assets/ and data/ from the jar into mods/<id>/carry/.
    2. Upgrade to 26.3. ATM10 is 1.21.1 and Rusty Minecraft is 26.3. Item models moved to items/ (1.21.4), recipe ingredients and results changed shape (1.21.2), some definitions moved to files of their own, and some registries and tags were renamed. The upgrader is a table of these changes generated from vanilla's own datafixers and pack-format notes, applied per file. A file it cannot upgrade is listed, not guessed.
    3. Registrations. Block and item ids registered in Java code are read from the oracle (step 6): its facts exporter writes each mod block state's hardness, sounds, shapes, light, map colour and class chain. These are the same exporters that produce Rusty Minecraft's vanilla gameplay-facts.json, run on the modded game. The class chain picks the template (a DoorBlock → a vanilla door). Without an oracle, the blockstate's property set gives the template (facing, half, hinge, open, powered is a door), with the template's numbers.
    4. The pack's own data. KubeJS scripts, Almost Unified and config-driven recipes change recipes, tags and loot after load. We do not translate scripts. The oracle exports the final recipe, tag and loot registries of the whole pack once, and the pack layer carries those over.
    5. Write <id>.hmod. For a data-tier mod, it is now ported.

    5. Code: one agent per mod

    For tiers logic, machines and deep, in dependency order, as many agents at once as the AI budget allows:

    • Input: the inventory record, the carried-over data, the oracle's exports and traces, the harness, native-mods.md, the ports of its dependencies, and the mod's public documentation. Never its code: the agent doesn't decompile, read or quote it.
    • Output: a native mod, a horizon-mixins bundle started from horizon-native-mod-template, and its .hnmod.
    • Loop: write → build → run the harness → read the differences → fix, until the harness passes or the agent reports what blocks it. Usually that is a place in the game's code the mixins can't reach yet, which becomes an issue ("needs a scheduled-tick hook point"), the way version ports turn differences into work items.
    • Rules: the agent writes the port from observed behaviour, the harness and the mod's own data files only; ports follow the mod's licence (Licences). Players without an AI agent get the carry-over tiers. A port the licence lets us publish can be downloaded instead of regenerated.

    6. The Java oracle and per-mod harnesses

    The oracle is dev-only, like Rusty Minecraft's vanilla oracles in tools/: the pack's own Minecraft version (1.21.1 for ATM10) with NeoForge or Fabric, the mod and its dependencies, plus a small exporter mod (written by us, never shipped to players). It runs headless and is driven over a socket, as the vanilla oracles are.

    A harness per mod, generated from the tier:

    Tier What is compared, oracle vs Rusty Minecraft with the port
    data every registered block state's facts (hardness, sounds, shapes, light, map colour, drops via loot), every item's facts, every recipe's result for its inputs, loot table outputs over fixed seeds, tags; structure placement over fixed seeds and chunks
    logic scripted interactions: place, use, break, tick N times; the world diff and the inventories after each step
    machines a fixture world with the machine, its inputs and power: the output, energy and progress per tick over N ticks; the menu's slots and data values; NBT after save and load
    deep entity scenarios (spawn, tick N, positions and states, drops), and render captures where the look is the point, compared as images with a tolerance

    The comparison skips vanilla 1.21.1-versus-26.3 differences: it normalises ids and components through the step-4 upgrader and compares only the mod's own ids and effects.
