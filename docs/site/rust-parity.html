    Rusty Minecraft Rust rewrite status

    The behavior target is the repository's pinned Minecraft Java Edition 26.3. One-to-one vanilla gameplay parity is the acceptance criterion. It has not been reached, but the Rust game is now playable: the native client has a title screen and world management. It generates vanilla terrain with decoration and streams, lights and renders it. Survival play works: mining, placing, crafting, chests and furnaces, items, mobs, combat, hunger, health, sounds, and Anvil saves. The Rust workspace implements core arithmetic/random streams, world data and resident sections, scheduled tick ordering, geometry, contained fluid states, noise/density evaluation, biome and terrain generation kernels, material rules, and parts of feature placement and decoration. Movement/fluid interactions, registered attributes, hunger storage/ticks, synchronized player health and absorption, damage reduction, outer hurt gates, blocking-item damage, item durability and item-use start/tick/release/completion have scoped native comparisons. Shared inventory/equipment storage now binds item-use flags and lifecycle, while item templates, remainders, checked bundle weights and cooldown expiry have native comparisons. Item completion composes stack copies with remainder and cooldown effects and server inventory delivery. Consumable start/completion now composes food storage, native random streams and eating particles, with exact sound parameters and effect ordering checked against both pinned JARs. Consume effect bodies now cover status application/removal/clearing, sounds and random teleport attempts. Shared status instances implement hidden-chain updates, server/client countdown and client blending with native comparisons. Entity effect storage now binds consumable status changes and the effect tick loop, including expiration, periodic refresh and client particle selection. Registered effect behavior, notification side effects and full entity/world lifecycle bindings remain unfinished. All pinned block-survival families now have native differential coverage. Full simulation callbacks, complete chunk generation, entity behavior, networking, rendering and playable integration remain unfinished. The linked subsystem documents and hashed reports record the exact tested scope and remaining gaps. The horizon-assets crate now decodes pinned cuboid models, with all 2,883 bundled block-model JSON files and 2,457 synthetic cases compared against the actual client parser. Decoder scope and validation also include parent/texture resolution over 5,648 roots and cuboid baking over 7,100 roots with identity blockstate transforms. Blockstate resource decoding now matches all 1,288 bundled definitions and 1,351 synthetic cases; registry binding now also matches native selection across registered and special item-frame states. Weighted selection and multipart random draw consumption also match native traces. Transformed baking now checks every bundled model/rotation/UV-lock tuple and all XYZ quarter-turn combinations against native geometry by exact float bits. The native renderer now draws its controlled resident chunks from registry-bound, selected and transformed models, including binary cutouts, multipart connections, weighted stone variants and stepped lantern animation. All 16 scene selections match native model collection. These are not yet simulated gameplay blocks. Resident chunk meshing now preserves weighted variants and UV orientation when greedily merging matching cube faces, and uses native-checked neighbor visibility. Full block-catalog material support, lighting and chunk streaming remain unfinished. Neighbor face visibility now matches both reference JARs across 1,441,816 state pairs, including all pinned suppression-rule families. Animation metadata, frame sequences and tick-state selection now have native differential coverage, including all bundled animated texture metadata. GPU interpolation and game-loop synchronization remain unfinished.

    Completion criteria and playable builds

    The final deliverable is the complete Rusty Minecraft Rust game with one-to-one parity with pinned Java Edition 26.3, plus a playable Linux build that the user can download and test. The target platform is a Linux x86-64 desktop with an NVIDIA GPU (Vulkan) on Wayland. macOS and Windows are out of scope. The build must include a packaged native executable, required runtime resources, launch instructions, artifact checksums, and the tested OS/CPU/GPU configuration.

    The build is complete only after its packaged Rust game is launched and tested on the target machine: create/load a world, render terrain, use keyboard/mouse controls, move and interact, break/place blocks, use inventory/crafting, save, quit and reload. These launch checks accompany the full gameplay-parity suite; they do not replace it. Record failures and test limits. Compiler success, library comparisons and the existing Java packs do not establish a playable Rust build.

    Optimize FPS, frame pacing, memory use and render distance using matched scenes, worlds, settings and hardware after behavior is validated. Package and test on the target machine before declaring the rewrite complete. Commit and push verified development checkpoints regularly.

    Implemented foundation

These choices avoid Java object overhead in this slice; no whole-game memory, FPS, or render-distance gain has been measured.

    Packet-relative positions use X/Z/Y ordering; block-state storage indices use Y/Z/X ordering. Negative coordinate conversion must floor rather than truncate. The legacy RNG must retain Java's signed-int arithmetic and rejection rules; the xoroshiro RNG has a different bounded-int algorithm and bit selection. Positional factories preserve signed coordinate hashing and each stream's distinct seed derivation. The hash API accepts UTF-16 units so malformed surrogate sequences retain Java's replacement behavior. Gaussian sampling is still absent: a private probe found bit differences between Java Math.log and the platform logarithm, which must be resolved before its values and cached-draw behavior can be claimed. Storage entries never cross a word boundary. Vanilla's fill operation also writes padding and unused tail bits; imported words retain their original bits when a slot is changed. These details are covered by the differential corpus.

    Rust APIs return typed errors instead of Java exceptions. Storage lengths and indices use usize; raw decoded values use u32 bit patterns. Writes reject values above the nonnegative Java-int domain, including at width 32. Test output casts raw imported width-32 reads back to signed Java ints for comparison. Negative lengths and the complete Java object/API surface are not supported.

Health synchronization retains its selected data object through later callbacks.     Effect-modifier map storage

    The default fastutil object map now preserves native slot order, nullable keys and values, growth/shrink behavior and live indexed entry handles. Entry iterators invalidate their current handle on removal; older handles continue reading the live arrays at their stored indexes. Callback traversal captures the key array but reads values from the current array, including after a rehash. Writes through a stale entry into an empty slot do not make that key present.

    The map comparison matches 1,142,630 lines per reference classpath against pinned fastutil 8.5.18. Library and fixture Clippy pass. The gate includes collision clusters, equal-key identity retention, entry mutation/invalidation and traversal callback failure prefixes. Alternate constructors, custom default return values, compute/merge/bulk APIs and external structural mutation combined with iterator removal remain outside this scope. Effect-modifier and full gameplay integration remain unfinished.

    Effect attribute templates and permanent modifiers

    Effect modifier definitions now scale their amount with vanilla's wrapping amplifier addition and create a fresh modifier identity on each application. Application looks up the attribute instance, removes the current definition's modifier, then reads the indexed definition again before creating and adding a permanent modifier. This preserves callback changes between those operations. Missing attribute instances skip template access, and failures retain preceding map and attribute writes.

    The modifier comparison matches 1,421,730 lines per reference JAR across 3,317 fixtures. It executes native effect modifier methods with real attribute instances, including cached values, permanent membership, dirty observers, nonfinite arithmetic, identity, map rehashes and callback failures. Library and fixture Clippy pass. The fixture asserts actual holder hashes when constructing collision cases. Attribute-map lookup and dirty callback receivers remain controlled. Registered effect definitions, pending queue ownership, entity bindings and complete gameplay/ platform builds remain unfinished.

    Attribute-map creation and live queues

    Effect modifiers now have a concrete attribute-map storage path with separate instance lookup, update and synchronization collections. Lazy creation copies the supplier before inserting the instance into the lookup map. Its dirty callback adds the update entry before checking synchronization eligibility, so a failed creation can leave an instance queued without a lookup entry. Later lookups can create a second instance while the first remains queued. Successful creation uses an ordinary map insertion after the callback, preserving callback replacement, resize and alias behavior.

Basic-attribute default/synchronization methods remain controlled callbacks; the fixture covers queue and lookup mutation but not arbitrary recursive instance mutation. Registered definitions, entity notification binding, bulk map methods and complete gameplay/platform builds remain unfinished.

Instance handles retain their identity independently of pending queue membership. Queries and base resets leave absent instances uncreated; effect application uses the same stored instance and queues as direct edits.

    Scoreboards, teams and subtitles

    tools/test_scoreboard_parity.py runs vanilla's own Scoreboard (what ServerScoreboard extends) and horizon_client::scoreboard on 500 scripted cases, about 81,000 operations: objectives with every kind of criteria (custom, team kill, and statistics in every spelling ObjectiveCriteria.byName accepts, which resolve to their canonical names), display names, render types, auto-updated displays and number formats; scores set, added, read, locked, given displays and formats, reset, and changed through forAllObjectives as the gameplay criteria change them; display slots; teams with every option, joined, left, removed and emptied by Scoreboard.entityRemoved. Every result must match, as must each collection in the order vanilla iterates it (objectives, holders and teams are fastutil open hash maps, each team's members a HashSet; fastutil_order keeps the same tables), the ScoreboardSaveData.Packed codec output that data/minecraft/scoreboard.dat holds (fields equal to the codec defaults are left out, components are written as ComponentSerialization writes them), and the data after each side loads the other's NBT.     tools/test_team_rules_parity.py runs vanilla's Entity.doTeamsAllowDamage (friendly fire), isAlliedTo, EntitySelector.pushableBy (collision rules), Entity.isInvisibleTo (seeing invisible team mates) and LivingEntityRenderer.shouldShowName (name tag visibility, with a stand-in client) on stand-in entities over 6,000 combinations of two teams' options and the entities' teams; the game uses the same functions. Mobs on the player's team never target the player, a creeper's blast spares its team mates when friendly fire is off, mobs push each other only as their collision rules allow, name tags show the team's prefix, suffix and colour and the score of the objective displayed below names, and a team that hides death messages keeps the player's own death message out of chat. The criteria that follow the player (health, food, armor, xp, level, air) update as ServerPlayer.doTick does, and deaths, kills, team kills and statistics update their objectives.

    tools/test_subtitle_parity.py runs vanilla's SubtitleOverlay with a stand-in client on 1,500 scripted cases of sounds reported by the sound engine (subtitles from sounds.json, positions, ranges, looping) at controlled times, and frames that render it for a listener transform, the subtitle options (shown or not, notification display time, text background opacity) and a GUI size. Every frame's fills and texts, with their pose, must match the overlay in hud_overlays: which captions show and in what order, merging of repeats, expiry, the fade by age, the direction arrows and the box width. The overlay listens to the sound engine from the frame that renders it with the option on until one renders with it off, as vanilla's does.

    Not covered yet: the player's air supply (Rusty Minecraft does not track drowning, so the air criteria stays at 300); displays auto-updated with the player's name carry the team formatting but not the click, hover and insertion of Player.getDisplayName; there is no attack sweep for allies to be spared from; scores below other players' names need the multiplayer scoreboard packets, which the client does not handle yet.
