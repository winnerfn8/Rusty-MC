    Rusty Minecraft native client

    horizon-client is the playable Rust client for Minecraft Java Edition 26.3. It streams a world around the player on worker threads, renders every vanilla block model with smooth lighting and biome tints, and runs the validated player physics, health and hunger at 20 ticks per second. You can mine with vanilla hardness/tool rules, collect drops from the block loot tables, place blocks, craft in the 2x2 inventory grid or on a crafting table, and save and reload worlds in vanilla's Anvil format.

    Status: playable; players get it through the launcher. The Java parity table in the README scores each subsystem against vanilla and lists what is still missing; Rust rewrite status has the details.

    Run from a checkout

    Use current stable Rust (1.90+) and JDK 25 (Python 3.10+ only for the development harnesses). A checkout never downloads the game: resource preparation imports your own copy (the 26.3 client from your official launcher install, and the 26.3 server jar you downloaded yourself; see Build from source), verifies it against the pinned checksums, runs vanilla's data generator and small exporters against those jars, and extracts the jar's assets and data into ignored .local/horizon-client/26.3/. Sounds (about 380 MB) are copied from your launcher's asset store by horizon-prepare sounds, each file checked against the asset index's SHA-1. Preparation also tries to replace the JAR's gray 1×1 title panorama placeholders with the full textures from that asset store. If the store is missing or incomplete, preparation logs a warning and keeps the placeholders. To import the panorama later without rerunning the Java exporters, run horizon-prepare panorama (or cargo run --release -p horizon-prepare -- panorama in a checkout). Pass --minecraft-dir PATH when using a different Minecraft installation. Prepared resources are private; never commit them.

    Preparation is horizon-prepare (crates/horizon-prepare, Rust): it needs no Python, only the JDK, for the small exporters that call Mojang's own code. Release folders ship it beside horizon-client, and the launcher prepares with it and copies the sounds as part of preparing.

    cargo run --release -p horizon-prepare -- --prepare --server-jar ~/Downloads/server.jar
cargo run --release -p horizon-prepare -- sounds
cargo run --release -p horizon-client -- --render-distance 12

    Development builds that link quickly: cargo build --profile fast -p horizon-client.

    Optional Windows allocator build features are documented in Windows allocator experiments.

    Option Meaning

    Worlds autosave every 6000 ticks (5 minutes), when chunks unload and on quit. On headless Linux use vscreen start ./target/release/horizon-client and vscreen shot.

    Sound: the game prints the output it opened (Rusty Minecraft: audio output ...) or why it has none (Rusty Minecraft: no sound: ...). It opens none with HORIZON_NO_AUDIO set, nor on a vscreen, where tests run beside someone listening; HORIZON_AUDIO=1 opens it there anyway, so send it to a null sink (PIPEWIRE_PROPS='{ target.object=<sink> node.dont-fallback=true }'). Don't mute a test run's stream in the mixer: PipeWire remembers the mute for every later horizon-client. The launcher starts the game as "Rusty Minecraft" for that reason.

    Agent control (horizon-ctl and MCP)

    AI agents and scripts play Rusty Minecraft through horizon-ctl, a command line that reads the game as JSON and acts like a player, and horizon-ctl mcp, an MCP server with the same commands. --control makes the game accept them on a local socket; under control, losing window focus does not pause the game or release held keys, so a script can play while you use other windows.

    cargo build --release -p horizon-client --bins
C=target/release/horizon-ctl
$C launch --world Survival --seed 5 --wait   # start the game, open or create the world, wait for it
$C state                                     # player, world, screen, crosshair target
$C find-block birch_log                      # the 16 nearest loaded logs
$C goto -0.5 65 -2.5 --near 2.5              # walk there along a path
$C break -1 65 -3                            # mine it: {"drops": {"minecraft:birch_log": 1}, ...}
$C inventory                                 # hotbar, inventory, armor, offhand, counts
$C open-inventory                            # craft planks in the 2x2 grid:
$C click-slot 0; $C click-slot 100 right; $C click-slot 0; $C click-slot 200 shift; $C close
$C place 2 65 -2 --item birch_planks         # {"changed": true, "block": {...}}
$C pause; $C ui                              # the pause menu's widgets: ids, kinds, labels, bounds
$C click options; $C set fov 0.75; $C click done   # widgets by id
$C screenshot /tmp/view.png                  # PNG of the next presented frame
$C quit                                      # save and exit

    horizon-ctl help lists the commands by group and horizon-ctl COMMAND --help explains one with examples; horizon-ctl help --game lists what the running game accepts, test hooks included.

    • Observe: state (position, rotation, velocity, health, food, saturation, XP, effects, game mode, dimension, time, weather, the screen and what the crosshair points at), looking-at, entities [RADIUS] [TYPE] (mobs with ids and health, dropped items, orbs), block X Y Z, blocks X1 Y1 Z1 X2 Y2 Z2, light X1 Y1 Z1 X2 Y2 Z2, find-block BLOCK [RADIUS], inventory (stacks with their components as SNBT), screen (the open screen or title menu, its buttons and slots) and messages (chat, title, subtitle and action bar).
    • Move and act: move DIR SECONDS, jump, goto X Y Z (A* over standable blocks: steps up one block, drops up to three, avoids lava), look, look-at a point, block face or entity, attack [ID], break X Y Z, place X Y Z [--item ITEM], interact X Y Z (doors, chests, crafting tables), use-item [--hold S] (eat, drink, throw), select SLOT|ITEM, drop.
    • Widgets: ui lists every widget of the open screen (title menus, pause, options pages, inventories and menus): an id, its kind (button, slider with its 0..1 value, field, row, tab with selected, slot with its stack), the label and its bounds. Ids come from labels (FOV: 70 is fov, Video Settings... is video-settings, a world row is the world's name; a repeat gets -2), else row-0, field-0, and slots are slot-ID. click ID [right] [shift] clicks one as the mouse would and set ID VALUE moves a slider to 0..1; after a click, the next ui, click or set waits for the screen to be redrawn. Design and plans: agent-control.md.
    • Options: options-get [KEY...] gives every options.txt option by its vanilla key with its value and what it accepts ({"type": "int", "min": 30, "max": 110, "value": 70}; enums with choices, key bindings as key.keyboard.w); options-set KEY VALUE sets one, applies it at once and saves options.txt as the options screen does. A value the option refuses is an error saying what it accepts, not vanilla's silent reset.
    • Waits and events: wait-for screen NAME|widget ID|loaded|chat TEXT|event KIND [--timeout S] [--since SEQ] replies once the game gets there (a timeout is an error with "kind": "timeout"), so scripts don't poll. events [--since SEQ] lists what happened, oldest first, each with a seq and the tick: screen (from, to), chat (text), death, respawn, item (item, delta), dimension, world (opened, closed). Take last from events before an action whose event you then wait-for --since it, so a fast one isn't missed.
    • Screens: open-inventory, click-slot SLOT [right] [shift] (0-8 hotbar, 9-35 inventory, 100+ crafting grid, 200 result, 300+ containers, 500-503 armor, 504 offhand, 600+ stations), close, click-button LABEL (any button of any screen or title menu, by its label), click-at X Y, type TEXT (on the create-world screen --field name|seed --replace), chat, command, respawn, pause, resume.
    • World: tp, give, time, setblock, summon, wait TICKS, and the benchmarking commands bench, stats and fly (below).

    Actions block until they finish or time out and reply with the outcome: goto says whether it arrived, break what dropped and what was picked up, place the block placed. stop cancels the running action. Every reply is one JSON line; errors are {"error": "..."} objects, and the exit status is 0 on success, 1 when the game replied with an error, 2 for a usage error and 3 when the game cannot be reached or started. horizon-ctl script FILE (or stdin) runs one command per line with shell-like quoting and stops at the first error (--keep-going doesn't); sleep S waits. horizon-ctl - is the older form that reads stdin and keeps going.

    launch finds the game to start: --game PATH, else a horizon-client next to horizon-ctl (a build folder or a release folder), else the newest version the launcher installed (--version TAG picks another), run with its prepared resources from the game home, where the saves are. So after installing with the launcher, horizon-ctl launch --world X --wait is all an agent needs. Other arguments go to the game; its output goes to a .log file beside the socket.

    Logs and crash reports. Like vanilla, the game writes logs/latest.log in the game home ($HORIZON_HOME, else ~/.local/share/horizon; the dedicated server in its own folder) with lines like [12:04:31] [Render thread/INFO]: message, and at start archives the last run's as logs/<yyyy-mm-dd>-<n>.log.gz (seven a day). Messages still print on stderr as before. A panic on the main thread or a fatal error writes crash-reports/crash-<yyyy-mm-dd_HH.MM.SS>-client.txt (the error, its stack, the machine, the GPU, render settings, resource packs, the open world and the last 50 log lines) and the game exits with a non-zero code. horizon-ctl logs [--lines N] prints the end of latest.log and horizon-ctl logs --crash the newest report (the logs MCP tool returns the same). F3 + C held for ten seconds crashes the game on purpose, as in vanilla (the world is saved first); development builds also crash with HORIZON_DEBUG_CRASH=SECONDS, that long after the first frame.

    MCP. horizon-ctl mcp serves the Model Context Protocol over stdin and stdout (JSON-RPC 2.0, one message per line), with one tool per command and a JSON schema for each; screenshot returns the frame as an image. Register it in an MCP client as a stdio server with the command horizon-ctl and the argument mcp (--socket PATH before mcp to pick a socket).

    Transport. On Linux and macOS the endpoint is a Unix socket: $HORIZON_CONTROL, else $XDG_RUNTIME_DIR/horizon-control.sock, or --control-socket PATH (horizon-ctl --socket PATH). Windows has no Unix sockets: there the game listens on a random 127.0.0.1 port and writes {"transport":"tcp","port":N,"token":"..."} to the endpoint path (%TEMP%\horizon-control.json by default), readable only by its user; the client's first line must be auth TOKEN. Any endpoint path ending in .json selects that transport on Linux and macOS too.

    tools/agent_control_e2e.py checks it all on a virtual screen: it creates a world through the title menus, walks to a tree, breaks a log, crafts planks in the inventory screen and places one, through the CLI and through MCP.

    fly X1 Y1 Z1 X2 Y2 Z2 SECONDS [PITCH] moves the camera along a line at constant speed and replies with the same summary as bench (avg/1%-low FPS and p50/p95/p99/max frame times), plus CPU and GPU time per frame; the graphics benchmark is built on it. Frame times include waits for presentation, so bench reports what is on screen.

    Discord Rich Presence

    While Discord runs on the same computer, the player's Discord profile shows "Playing Horizon" and what they are doing: "In the menus", "Singleplayer", "Multiplayer" or "Hosting a world" (with the party size, of 8), the dimension ("In the Nether") and the time since they entered the world. It never shows a world's name or a server's address. Rusty Minecraft Settings has the switch (Discord Rich Presence, on by default; discordPresence in horizon-extras.txt), and HORIZON_NO_DISCORD=1 turns it off for one run.

    crates/horizon-client/src/discord_presence.rs speaks Discord's local IPC itself (the discord-ipc-N socket or named pipe, no SDK) from a thread of its own: the frame only hands it a status when it changes. It retries every 15 s while Discord isn't running and stays within Discord's 5 updates per 20 s. Dedicated servers never start it, and automated runs (offscreen, benchmarks) only talk to a fake Discord: lab.game_env sets HORIZON_NO_DISCORD=1, and tools/discord_presence_e2e.py points games at a fake server with HORIZON_DISCORD_IPC_DIR (title, world, Nether and quit on both single-player paths; a LAN host and guest; the switch; a Discord started after the game). DISCORD_APP_ID is Discord's "Rusty Minecraft" application, whose horizon image is the large one; there are no game-mode images yet.

    Play on another of your machines

    Rusty Minecraft targets Linux on x86-64 with an NVIDIA GPU (Vulkan); macOS and Windows are out of scope. To play on another Linux machine without Rust, JDK or prepared resources, package a release build where they exist:

    cargo build --release -p horizon-client
python3 tools/package_native_client.py --out ~/builds/horizon

    The archive holds the binary, the prepared resources and horizon.sh. Copy it to the target machine (same OS and architecture), unpack it and run horizon/horizon.sh; horizon.sh --install adds an application menu entry. Saves and options.txt go to ~/.local/share/horizon (or $HORIZON_HOME), so unpacking an update keeps them. The archive contains Mojang assets: keep it private.

    How it fits together

    • streaming.rs: worker pool that generates or loads, lights and meshes chunk columns closest-first; stale results are discarded by sequence number.
    • light.rs: vanilla sky/block light rules (sky sources down to the first occluding edge, max(1, dampening) falloff) over a 3x3 chunk region.
    • mesher.rs: blockstate models with neighbour culling, ModelBlockRenderer smooth lighting/ambient occlusion, BlockTintSources tints with 5x5 biome blending, and FluidRenderer water/lava surfaces.
    • gfx.rs + terrain.wgsl: camera-relative section rendering with frustum culling, the vanilla lightmap formula, timeline-driven sky/fog, and solid/cutout/translucent passes; entity.wgsl draws dropped items.
    • environment.rs: the data-driven day timeline (sky colour, light factor, celestial angles) sampled with vanilla's keyframe/easing rules.
    • items.rs, crafting.rs: item components from vanilla's reports, tool mining rules, loot tables and crafting recipes from the data pack.
    • save.rs: Anvil region files and level.dat.

    Validation

    The client loads a separate, registry-checked collision-shape export alongside render resources. SceneCollisions feeds its actual TerrainChunk instances into registered shape selection, block scanning, world movement resolution and occupancy checks. The scene has no other entities, block entities or border; entity-dependent queries report an error until an entity runtime is supplied. Camera collision uses a position context and disables stepping. The walking binding uses the current pose bounds, descending input and registered step-height attribute. Sneaking invokes ledge backoff before collision resolution. The complete authoritative player tick remains unfinished.

    cargo run --release -p horizon-prepare
python3 tools/test_native_scene_collision.py

    The scene collision comparison checks 14,150 movement requests, each with before/after occupancy queries, against both pinned reference JARs. Native code independently builds the nine- and twenty-five-chunk scenes and all sixteen gallery placements. Movement components compare by exact double bits. Cases include partial blocks, pyramid ledges, ceilings, initial overlaps, negative and missing chunk boundaries, tiny and zero movement, and varied step heights. This verifies the scene adapter; it does not establish player locomotion or complete gameplay parity.

    The movement binding stores a player's position, velocity, pose bounds, ground/support state, collision flags, movement history and live registered attributes. MotionWorld composes the existing air-travel, jumping, collision, ground-support, restitution and block-coefficient code over the same scene. The stored-motion comparison checks 42,257 operations across 637 evolving scenarios against actual native Player.travel, jumping and movement, using real native attributes and chunks. It compares every resulting position, velocity and bounding-box component by exact bits, along with support, climbing and collision state and both separate velocity/position synchronization flags.

    The dry movement tick additionally binds small-velocity cleanup, float input damping, held-jump delay and server frost-modifier removal. The expanded tick comparison checks 47,393 operations in 847 scenarios against both pinned JARs, including direct calls to the actual LivingEntity.aiStep body. It compares lazy attribute instance creation, stored base/cache/dirty state, modifier values and permanence, and pending update/sync membership alongside the motion fields. Queue iteration order depends on runtime identity hashes and is outside this scene comparison. The test caught an omission where matching positions concealed a retained powder-snow modifier and missing attribute notifications; dry ticks now remove that modifier after travel, as vanilla does.

    The walking movement comparison extends this to 65,893 operations in 947 scenarios, invoking actual Player.aiStep with empty inventory/equipment and no nearby entities. It checks head yaw, jump-trigger countdown and speed refresh after movement. Prepared input is supplied at the native virtual input boundary. Separately, the local input comparison checks 13,988 cases against actual KeyboardInput.tick and LocalPlayer.modifyInput, covering every key combination, diagonal adjustment, item/riding/sneaking speed gates, signed zero and nonfinite values. This verifies input arithmetic; the sprint and crouch integration checks below extend it. The full LocalPlayer lifecycle remains unfinished.

    The fixed-rate driver limits work per rendered frame while retaining overdue ticks. Clock tests cover varied frame schedules and long stalls. The development focus pause is explicit; no vanilla pause-menu or multiplayer timing is claimed. The Linux walking smoke check enabled F5, landed at ground height 4, walked, jumped, switched modes and exited with Ctrl+Q. Ground, moved and airborne screenshots were visually inspected; the run recorded 207 movement ticks and finished grounded without an error. The renderer startup check also passes after the movement integration.

python3 tools/test_native_scene_motion.py
python3 tools/test_local_input_parity.py

    This binding is not yet a complete player tick or input controller. Its current domain is the dry resident scene with standing/crouching/crawling dimensions, zero frozen ticks, empty inventory/equipment, and no entity interpolation, vehicles or status effects. Selected Player.aiStep phases are bound; the full tick and local input lifecycle remain unfinished. Landing now accumulates and resets the stored fall distance, clears climbing state on ground, and invokes registered block fall/bounce reactions. The composed landing comparison checks 73,025 operations in 1,449 scenarios against both pinned JARs. It compares fall state, impulse exemptions, attributes and ordered damage, statistic, particle, sound and hit-ground requests alongside the previous motion fields. Actual native LivingEntity.checkFallDamage, registered block methods and Player/LivingEntity.causeFallDamage execute in the reference harness. The cases include hay, honey, slime, powder snow, pointed dripstone, farmland, turtle eggs and shelf mushrooms, with seeded world randomness. Farmland pushes the stored player and changes the resident block to dirt; repeated egg changes preserve hatch state. The resulting block state is checked after each operation.

    The client refreshes its mesh after a resident block revision changes. This is a complete scene rebuild for now, with no performance improvement claimed. Damage requests are counted in runtime reports, and the health binding described below applies them synchronously. Full death/respawn, audiovisual playback and networking still need consumers. Block writes currently update resident storage; neighbor updates, drops and block-entity lifecycle remain unfinished. Block-inside effects such as cobweb slowdown and the full entity lifecycle are also unfinished. The reference harness explicitly controls these boundaries, which remain outside the comparison's scope. The earlier scene collision comparison and renderer startup also pass with this binding and the additional prepared movement resources.

    The accompanying startup check passes after sharing scene loading between the GUI and headless collision probe. An interactive Linux check enables F4, holds Shift to descend, verifies that the camera stops at the terrain surface, and exits with Ctrl+Q. The window was visually inspected on Vulkan llvmpipe; this is not a hardware performance measurement.

    The separate horizon-assets crate decodes the pinned 26.3 cuboid model format. Its native comparison covers all 2,883 block-model JSON files in the client JAR plus 2,457 synthetic cases: element bounds, optional geometry, nullable children, face UVs and quarter turns, single-axis/Euler rotations, texture references and translucency materials, light emission, display transforms and inheritance markers. Floating-point fields compare by their exact bits. The comparison also covers primitive coercion, integer truncation/wraparound and selected strict-reader numeric/syntax limits. The numeric scanner also preserves vanilla's rejection when its wrapping integer accumulator hits zero before another digit, including in ignored fields. Twenty newly exposed acceptance mismatches were corrected; the complete comparison now covers 5,340 models. The resolution, baking and animation comparisons also pass with the shared scanner correction.

The resolution comparison matches 5,648 requested roots across 439 graphs, including the full bundled block-model catalog, missing parents, 702 cyclic roots, 1,024-model parent chains, 512-slot alias chains, explicit empty geometry and identity/null transforms. It calls native ModelDiscovery, ResolvedModel and TextureSlots APIs.

Synthetic coverage includes reversed/degenerate bounds, signed zero, arbitrary rotations, rescaling, null geometry children and parent cycles. Position, UV and matrix fields compare by exact float bits for these fixtures.

    BlockModelTransform now prepares all 64 XYZ quarter-turn combinations once and shares them across baked models. It rotates geometry around the block center, rotates culling directions and applies UV locking in the original face basis. The transformed baking comparison checks every distinct model/rotation/UV-lock tuple in bundled blockstates and all 128 rotation/lock combinations on 81 synthetic models, plus further arbitrary element rotations. Positions, UVs and every orientation/inverse-face matrix compare by exact float bits: 19,704 roots and 148,439 quads match, including 7,884 bundled model/transform tuples. Quaternion basis rounding and numeric identity rechecking are retained. This remains geometry validation; atlas packing and pixel parity are separate work.

    python3 tools/test_blockstate_transform_parity.py

    Blockstate resources now decode into ordered variant selectors and multipart conditions. The Rust representation preserves single versus weighted variants, all three quarter-turn axes, UV-lock flags, positive weights and total-weight limits, ordered selectors, nested AND/OR conditions and per-term negation.

    Property binding now selects variant roots or multipart part indices for an ordered native state list. The binding comparison covers all 1,288 bundled definitions against 35,723 registered block states plus the four special item-frame states, followed by synthetic overlap, malformed selector and predicate cases: 3,802 definitions and 687,466 state results match, with 220 expected binding errors. It checks the native replacement-before-abort behavior for overlapping variants, eager multipart validation even when variants cover every state, integer-property aliases, nested conditions and empty part selections. The controlled chunk renderer now uses this binder for its model catalog.

    The Java integer-property parser is shared by horizon-core, client binding and world-state decoding. Its codec regression matches 221,261 output lines against each authenticated client/server JAR.
